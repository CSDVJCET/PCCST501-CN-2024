Wireshark Based Experiment

🔎 Lab 2: HTTP Conversation Investigator

Capture one HTTP browser–server conversation and reconstruct the request, response, accepted content preferences, status information and response time.

Experiment02
ToolWireshark
ProtocolHTTP
EvidenceConversation Case File

🎯 Aim

To capture and analyse HTTP request and response messages using Wireshark, identify the communicating endpoints and HTTP header fields, and calculate the delay between a GET request and its corresponding response.

⚠️ Before You Capture

Important: Most modern websites use HTTPS, so the HTTP application data is encrypted and may not appear with the http display filter.

Use an instructor-approved plain HTTP test page. Capture only your own permitted lab traffic. Some HTTP headers such as Accept-Charset, Last-Modified or Content-Length may be absent in a particular message; if so, record Not present rather than inventing a value.

🧪 Capture Procedure

1️⃣ Prepare the Browser

Open the browser and clear its cache so that the page is requested again from the server instead of being served from cached content.

2️⃣ Start Wireshark

Select the active network interface and begin packet capture before opening the test webpage.

3️⃣ Generate HTTP Traffic

Visit the instructor-approved plain HTTP webpage once and wait until the page request and response are captured.

4️⃣ Stop and Filter

Stop packet capture after enough packets have been collected. Apply this Wireshark display filter:

http

🕵️ Investigation Tasks

(a) First GET Message — Endpoints

Locate the first HTTP GET request and record its source IP address and destination IP address.

(b) Client Content Preferences

Using the first GET request, inspect these HTTP request headers:

  • Accepted media format: Accept
  • Accepted language: Accept-Language
  • Accepted encoding: Accept-Encoding
  • Accepted character set: Accept-Charset, if present
(c) Requested Website and User Agent

From the first GET request, record the website/resource URL and the User-Agent value.

(d) First Response Message — Endpoints

Locate the response corresponding to the GET request and record its source and destination IP addresses.

(e) Response Status

Record the HTTP status code and reason phrase from the first response message.

(f) Last Modification Time

Record the value of the Last-Modified header. If the server does not send it, write Not present.

(g) Content Length

Record the value of the Content-Length header. If absent, write Not present.

(h) GET-to-Response Delay

Record the timestamp of the GET request and the timestamp of its corresponding response.

Response delay = Response timestamp - GET timestamp

Report the result in seconds.

(i) Browser HTTP Version

Record the HTTP version shown in the request line of the first GET message.

🏁 Student Challenge

Tell the HTTP Story

Using your captured evidence, explain the conversation in six sentences:

  1. Who sent the GET request and to whom?
  2. What resource was requested?
  3. What media, language, encoding and character-set preferences were advertised?
  4. Which browser/client software was identified?
  5. How did the server respond?
  6. How long did the request–response exchange take?

❓ Viva Questions

  1. Why should the browser cache be cleared before this experiment?
  2. What is the purpose of an HTTP GET request?
  3. Why are the source and destination IP addresses reversed in the response?
  4. What is the difference between Accept and Accept-Encoding?
  5. What does the User-Agent header identify?
  6. What does an HTTP status code indicate?
  7. Why might Last-Modified or Content-Length be absent?
  8. How is the GET-to-response delay calculated?
  9. Where is the HTTP version visible in a request?
  10. Why does the http filter usually not reveal ordinary HTTPS application content?
